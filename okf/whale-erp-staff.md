아니라 고치기 화면에만 있다. 넣은 쪽만 보낸다 — 주민등록번호만 · 급여 계좌(은행 + 계좌번호 함께)만 · 둘 다, 둘 다 비었거나 은행 · 계좌번호 한쪽만이면 화면에서 막는다(서버 액션도 다시 거른다). 주민등록번호 앞자리 · 뒷자리 첫 자리가 가입 생년월일과 다르면 데모처럼 칸 아래 오류와 함께 저장 버튼을 막고, api 의 400 `RRN_BIRTH_MISMATCH` 도 같은 문구다. 서버 액션 `saveTaxProfileAction`(소속 id 는 bind)은 먼저 `GET` 으로 신고 정보가 있는지 보고 없으면 PUT 하지 않는다(`taxProfileEditBlocked`, 액션은 누구나 직접 부를 수 있어 버튼을 숨긴 것만으로는 첫 입력을 막지 못한다). 이 조회가 실패하면 저장 실패와 같은 안내다(404 는 「소속 근무지에서 다시 열어 주세요」, 503 은 api 사유 대신 「신고 정보를 저장하지 못했습니다. 잠시 뒤 다시 시도해 주세요」). 값을 고치거나 다시 보내는 동안에는 지난 서버 오류를 가린다. 400 은 본문 `code` 로 가르고(`failureOf` 가 `ApiFailure.code` 로 넘긴다), 404 · 429 · 503(api 사유 대신 고정 문구 「신고 정보를 저장하지 못했습니다. 잠시 뒤 다시 시도해 주세요」) · 500(계속되면 점포에 알림)은 버튼 위. 성공하면 보기 화면으로 replace 하고 `?changed=1` 로 「신고 정보를 바꿨습니다」 알림(`ChangedToast` 의 `path`). 돌아온 보기 화면의 조회가 실패해도 알림을 띄우고 주소의 `?changed=1` 을 지우며, 안내를 「신고 정보를 바꿨습니다. 바뀐 값은 지금 볼 수 없으니 잠시 뒤 다시 열어 주세요.」로 바꾼다(`taxViewAfterChange`, `ChangedToast` 는 children 이 없으면 주소만 지운다). 주민등록번호 원문은 서버 액션 상태 · 로그 · 주소 · 쿠키에 싣지 않는다 — 넣은 값은 화면 상태로만 들고, 하이드레이션 뒤에는 onSubmit 이 막고 직접 보낸다(React 19 폼 액션의 자동 reset 이 고른 은행을 비워 상태와 어긋났다). `action` 에도 서버 액션을 두어 하이드레이션 전 제출은 서버 액션 POST 가 된다 — action 없는 폼은 기본 GET 이라 원문이 주소에 붙는다(PR #26 리뷰). 소속 id 는 서버 화면(page.tsx)에서 bind 해 넘긴다 — 클라이언트 컴포넌트에서 렌더마다 bind 하면 하이드레이션 전 POST 에 서버가 응답하지 않았다(2026-10-23 재현). 입력 칸은 자동 완성을 끈다. 뒷자리 칸은 `type="password"` 가 아니라 글자 칸을 CSS(`-webkit-text-security: disc`)로 가린다 — 저장 뒤 브라우저가 「비밀번호 저장」을 띄워 원문이 브라우저 · 동기화에 남지 않게(비밀번호 관리자 확장도 `data-1p-ignore` · `data-lpignore` 로 무시). CSS 가림은 값이 그대로라 뒷자리 칸의 복사 · 잘라내기 · 끌어 옮기기를 막는다(붙여넣기는 둔다, 화면 낭독기는 본인 입력 확인이라 막지 않는다). 계약 어긋남으로 남기는 로그에는 api `code` 도 함께 남긴다. 입력 칸(`src/app/_components/tax-profile-fields.tsx` 의 `RrnField` · `PayrollAccountFields`)과 보기 조각 · 문구(`tax-profile-parts.tsx` 의 `Sunken` · `Values` · `Basis` · `RRN_BASIS` · `ACCOUNT_BASIS` · `TaxOwnerNotice` · `TaxIdentity`)는 150 이 그대로 쓸 수 있게 따로 두었다(값은 쓰는 쪽이 상태로, `required` 는 처음 넣기용). 순수 계산은 `src/lib/tax-profile.ts`(`parseStaffMemberId` · `rrnBirthMismatch` · `readTaxProfileForm` · `validateTaxProfileEdit` · `taxProfileEditBlocked` · `taxProfileSaveFailure` · `window.daum` 으로 준비를 가른다)를 바텀시트에 embed 해 도로명(`roadAddress`, 비면 `autoRoadAddress`)과 우편번호를 고르고 상세 주소만 적는다(ME-2). 저장은 서버 액션 `saveAddressAction`(`PUT /me/profile/address`) — 실패하면 넣은 값은 그대로 두고 오류와 「다시 하기」, 성공하면 공통 `Toast`(「변경사항을 저장했습니다」). 위치정보 동의 카드(ATT-23 · 26)는 같은 크기의 작은 버튼 세 칸이 자리를 지키고 가운데 「잠시 멈춤 ↔ 다시 켜기」, 오른쪽 「동의 철회 ↔ 다시 동의」만 바뀐다(2026-10-20 노영주, 데모는 다시 켜기 · 다시 동의하기가 큰 버튼). 미동의 · 철회면 잠시 멈춤은 흐리게 둔다. 내 * `src/proxy.ts` - 접속 유지. 액세스 토큰이 없고 갱신 토큰이 있으면 `/auth/account/refresh` 로 다시 받아 응답·요청 쿠키에 굽고, 갱신이 401 · 400 이면 쿠키를 지우고 `/login?expired=1` 로 보낸다. 그 밖의 실패(api 미기동 · 5초 시간 초과 · 429 · 5xx)는 접속이 끝났다고 단정하지 않고 쿠키를 둔 채 로그인 필요 화면과 만료 안내에서는 `/login?unavailable=1` 로 보낸다(그 밖의 공개 화면 `/login` · `/password-reset` · `/email-find` · `/join` · `/invite` 는 그대로 연다). `/login?unavailable=1` 도 만료 안내처럼 갱신에 성공해야 로그인으로 친다 — 남은 액세스 토큰만 보면 `/home` 으로 튕겨 다시 401 → 만료 안내를 돈다. `/login?expired=1`(서버 컴포넌트가 401 을 받거나 세션을 못 읽으면 이리로 보낸다)에서는 갱신을 해 보고 정말 끝났을 때(401 · 400)만 쿠키를 지운다 — 살아 있으면 다시 굽고 `next`(없으면 `/home`)로 보낸다. 주소만으로 지우면 다시 로그인한 뒤 뒤로 가기 · 새로 고침이나 남이 건 링크로 접속이 끊긴다. 읽히지 않거나 모양이 다른 `account` 쿠키는 세션으로 치지 않고 지운다 — 판정은 화면의 `getSession` 과 같은 `parseAccountCookie` 다. 로그인 필요 경로 판정도 여기서 하되, 화면·액션은 `requireSession()` 을 따로 거친다. 갱신이 401 · 400 이거나 account 쿠키가 손상돼도 로그인 없이 여는 화면(`/login` · `/password-reset` · `/email-find` · `/join` · `/invite`)은 쿠키만 지우고 그대로 연다 — 다른 기기에서 비밀번호를 바꿔 접속이 끝난 직원이 재설정으로 바로 가게 한다. `/design` 과 그 아래 · 정적 파일은 빼고 돈다. 로그인 화면(`/login` · 만료 안내 · 확인하지 못함 안내)으로 보낼 때는 보던 경로 + 쿼리를 `next` 로 싣고(홈이면 싣지 않음), 로그인돼 있는데 `/login` 이면 `next` 로 보낸다 — 만료 안내에서 갱신해 보니 살아 있던 경우도 같다(WHALEERP-166). 로그인이 필요한 화면으로 통과시키는 요청에는 지금 경로를 `x-staff-path` 헤더로 넘긴다(브라우저가 보낸 값은 덮어씀).
