API 호출 아키텍처whale-erp-staff

이 콘솔은 데이터를 직접 갖지 않는다. 화면에 뜨는 모든 값은 whale-erp-api 가 준 것이고, 그 호출은 전부 Next.js 서버 안에서 일어난다. 브라우저는 API 주소도 액세스 토큰도 보지 못한다. 아래는 현재 동작하는 로그인과 품목 목록을 기준으로 그 구조를 정리한 것이다.

경계가 먼저다

이 구조의 출발점은 보안 취향이 아니라 제약이다. whale-erp-api 에는 CORS 설정이 없다. 그래서 브라우저가 API 를 직접 부르는 경로는 애초에 막혀 있고, 남은 선택지는 Next.js 서버가 대신 부르는 것뿐이다. 그 결과 액세스 토큰과 API_BASE_URL 이 브라우저로 내려갈 이유가 사라졌다.

호출은 두 갈래뿐이다

화면이 API 를 부르는 방법은 두 가지고, 새 기능도 이 둘 중 하나에 들어간다. 읽기는 서버 컴포넌트가 렌더 중에 부르고, 쓰기는 서버 액션이 폼 제출을 받아서 부른다. 둘 다 lib/api.ts 를 지나므로 인증과 오류 처리를 한 곳에서 끝낸다.

읽기: 세션 확인이 첫 줄이다

// src/app/items/page.tsx
export default async function ItemsPage() {
  const session = await getSession();
  if (!session) redirect("/login");

  try { items = await listItems(); }
  catch (error) {
    // 액세스 토큰이 15분을 넘겨 만료되면 401 이다. 다시 로그인시킨다.
    if (error instanceof ApiError && error.status === 401) redirect("/login");
    throw error;
  }
src/app/items/page.tsx:5-16

401 을 만나면 화면에 오류를 띄우지 않고 로그인으로 되돌린다. 이 콘솔에서 401 은 예외 상황이 아니라 15분마다 정상적으로 도달하는 상태라서 그렇다. 그 밖의 오류는 삼키지 않고 그대로 올린다.

쓰기: 실패의 종류를 나눈다

// src/app/login/actions.ts
catch (error) {
  if (error instanceof ApiError) return { error: error.message, email };
  if (error instanceof TypeError) return { error: "API 서버에 연결하지 못했습니다", email };
  throw error;              // 환경 변수 누락 같은 설정 문제는 감추지 않는다
}
redirect("/items");        // try 밖. redirect 는 내부적으로 예외를 던진다
src/app/login/actions.ts:21-32

세 갈래다. ApiError 는 사용자가 고칠 수 있는 문제(비밀번호), TypeError 는 API 가 떠 있지 않은 문제, 나머지는 개발자가 봐야 할 문제다. 마지막 것을 화면에 예쁘게 감싸지 않는 것이 이 코드의 판단이다. redirect 를 try 밖에 둔 이유도 같다. 안에 두면 catch 가 삼킨다.

호출 지점이 하나인 이유

모든 호출이 src/lib/api.ts 의 request() 를 지난다. 화면마다 fetch 를 흩어 놓지 않았기 때문에 아래 네 가지를 한 번만 처리하면 된다.

규칙코드없으면 생기는 일
주소를 호출 시점에 읽는다 function baseUrl() 안에서 process.env 접근 .env.production 이 비어 있어 빌드 시점에 읽으면 undefined 가 굳는다. 값은 배포 환경이 주입한다.
빈 값에서 즉시 멈춘다 if (!url) throw fetch("undefined/items") 로 번져 원인을 찾기 어려운 오류가 된다.
캐시하지 않는다 cache: "no-store" 사용자마다 다른 응답이라 캐시하면 남의 데이터가 보인다.
Nest 오류를 한 모양으로 만든다 ApiError(status, message) 검증 실패 시 message 가 배열로 와서 화면마다 다르게 깨진다. 배열이면 join(", ").
204 를 파싱하지 않는다 status === 204 ? undefined : json() 본문 없는 로그아웃 응답에서 json() 이 터진다.
토큰을 붙이는 일은 호출부가 한다 request() 자체는 인증을 모른다. listItems() 와 logout() 이 getSession() 으로 토큰을 꺼내 Authorization 헤더를 만든다. 덕분에 로그인처럼 토큰이 없는 호출도 같은 함수를 쓴다.

세션은 15분 뒤 절벽을 만난다

쿠키 maxAge 를 액세스 토큰 수명과 같은 900초로 맞춰 놓았다. 그래서 쿠키가 살아 있는 동안은 토큰도 살아 있고, 둘이 거의 같이 죽는다. 리프레시 토큰은 받아 놓고 버린다. 회전이 구현되지 않았으므로 15분마다 다시 로그인한다.

15분은 화면 설계에도 영향을 준다 작성 중인 폼을 들고 있다가 만료되면 입력이 사라진다. 지금 구현된 화면은 읽기 전용이라 문제가 드러나지 않지만, 직원 앱의 계약서 날인이나 TO-DO 처리처럼 쓰기가 들어오면 회전 없이는 곤란해진다.

지금 쓰는 엔드포인트

코드에서 실제로 호출하는 것은 넷이다. 나머지는 API 에 있으나 화면이 아직 부르지 않거나, 아직 없다.

엔드포인트부르는 곳인증상태
POST /auth/staff/loginlogin() ← loginAction없음호출 중
POST /auth/logoutlogout() ← logoutActionBearer호출 중
GET /items?take=50listItems() ← ItemsPageBearer호출 중
POST /auth/refresh없음refreshToken미사용
품목 등록 · 수정 · 삭제없음BearerAPI 는 있음 · 화면 없음
재고 이동 기록없음BearerAPI 는 있음 · 화면 없음
총 건수 조회없음-API 없음
직원 회원가입없음-API 없음 · 계정은 운영자가 발급

take 는 API 가 최대 200 까지 받는다. 총 건수 API 가 없어서 품목 화면의 숫자는 받아온 배열 길이(items.length)이며, 200 을 넘는 순간 실제 총계와 어긋난다.

직원 앱을 얹을 때 깨지는 곳

지금 구조는 브라우저 하나에 직원 하나를 전제한다. 세션 쿠키가 곧 신원이기 때문이다. 직원 모바일 앱은 이 전제를 그대로 만족하므로 위 구조를 그대로 확장하면 된다. 문제는 디자인 시안의 매장 출퇴근 등록 앱이다. 한 단말을 여러 직원이 번갈아 쓰므로 전제가 깨진다.

화면과 호출의 대응

아래 엔드포인트는 아직 API 에 없다. 시안의 화면이 무엇을 요구하는지 정리한 것이며, 이름은 제안이다.

화면필요한 호출경로
홈 · 오늘/이번 주 근무GET /staff/me/shifts?from&to읽기 · 서버 컴포넌트
근무스케줄GET /staff/me/shifts (주 단위)읽기 · 서버 컴포넌트
출퇴근 현황GET /staff/me/attendances읽기 · 서버 컴포넌트
급여명세서GET /staff/me/payslips · 발송된 것만읽기 · 서버 컴포넌트
근로계약서 목록 · 상세GET /staff/me/contracts읽기 · 서버 컴포넌트
날인 · 거부POST /staff/me/contracts/:id/sign쓰기 · 서버 액션
TO-DO 완료 처리PATCH /staff/me/todos/:id쓰기 · 서버 액션
연락처 수정PATCH /staff/me/contact쓰기 · 서버 액션
매장 출퇴근 등록POST /attendances · 단말 자격 + 직원 식별값쓰기 · 별도 인증
근무지 전환은 조회 범위를 바꾼다 시안의 근무지 칩은 화면 필터가 아니라 질의 범위다. 여러 근무지에 연결된 직원의 모든 조회에 근무지 식별자가 따라붙어야 하므로, 선택값을 어디에 두느냐(URL 세그먼트 · 검색 파라미터 · 쿠키)를 화면을 짜기 전에 정해야 한다. 서버 컴포넌트가 읽어야 하는 값이라 클라이언트 상태로는 부족하다.

먼저 결정할 것

  • 리프레시 회전. 쓰기 화면이 들어오기 전에 채워야 한다. 미들웨어와 라우트 핸들러 중 어디에 둘지가 실제 결정이다.
  • 매장 단말 인증. 단말 자격을 어떻게 발급하고 폐기할지. 직원 식별 방식(QR · 바코드 · 매장 PC)이 확정되어야 이어서 정할 수 있다.
  • 근무지 범위를 어디에 둘지. URL 에 두면 공유와 새로고침에 강하고, 쿠키에 두면 화면이 단순해진다. 서버 컴포넌트가 읽는다는 조건은 같다.
  • 총 건수 API. 페이지네이션이 필요한 목록(출퇴근 기록, 급여명세서)이 생기면 take/skip 만으로는 부족하다.
